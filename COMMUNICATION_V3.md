# Communication V3 Domain Contract

Empirical qualification results and retained evidence are documented in
[`docs/communication-v3-qualification.md`](docs/communication-v3-qualification.md).

This contract is the scheduler and coordination source of truth. The executable
request reducer lives in `packages/core/src/coordination-v3.ts`. Authorization,
idempotency, and persistence surround that pure reducer.

Communication V3.3 is unconditional. There is no executable V2 scheduler,
feature flag, migration reader, or compatibility delivery ledger. Deployments
reset pre-cutover test data instead of replaying ambiguous scheduler state.

## Objects and ownership

- **Agent:** durable identity.
- **Request:** ephemeral, correlated work or consultation between a requester
  and one recipient. It can progress without the requester waiting.
- **Join:** durable condition over an immutable set of request IDs.
- **Activation:** actionable, prioritized reason to wake an agent.
- **Trigger:** durable user-authored automation owned by exactly one existing
  Agent in one Project chat.
- **Trigger occurrence:** immutable, deduplicated source event and provenance.
- **Run:** temporary execution consuming one or more compatible activations.
- **Provider session:** resumable cache owned by one agent, never agent identity.
- **OS process:** evictable implementation detail.

SQLite is authoritative for request and join state, activations, run identity and
status, activation attachment and consumption, leases and fencing tokens,
prompt-injection state, terminal outcomes, idempotency, and the activation outbox.
JSONL may retain rich runtime telemetry, but it is not a competing scheduler
authority.

Provider-session continuity follows durable causal scope. A newly created
inbound coordination request starts a fresh task session for its recipient.
Updates within that request, human steering, and join resumptions retain their
current session. Rolling the provider cache never changes agent identity,
messages, files, request state, or join ownership. Request text is therefore
self-contained: recipients do not inherit the requester's hidden prompt or
provider-session context.

Fresh-task request Activations and continuity Activations are incompatible for
Run coalescing. If both are pending, scheduler priority chooses the first Run
and leaves the other class pending for the next authoritative Run, so a human
message or join resumption can never receive an ambiguous cache disposition.

## Trigger ownership and intake

A Trigger exists only at `Project → Project chat → Agent → Triggers`. It cannot
target multiple Agents, cross a Project-chat boundary, or outlive its Agent or
chat membership. Deleting the Agent, deleting that Project chat, removing the
Agent from that chat, disabling the Trigger, or deleting the Trigger stops new
intake and cancels work that has not begun. Historical completed Runs, managed
artifacts, and occurrence rows remain inspectable until their Project is deleted.

V3.2 supports one-time, interval, and timezone-aware cron schedules; signed JSON
webhooks; and changes below the Project's configured host folder.

Every normalized source event is one immutable Trigger occurrence. Stable
`(triggerId, occurrenceKey)` identity makes exact source retry idempotent and
rejects a conflicting payload. An occurrence creates exactly one Activation;
only the scheduler may create its Run. Trigger Activations always use
`next_run`: they never steer an active provider turn. Compatible pending
occurrences from the same Trigger may be coalesced into one bounded Run while
retaining every occurrence ID, order, payload hash, and provenance. Different
Trigger definitions never share a Run. Events arriving during an active Run
remain queued for the next batch.

Filesystem intake groups low-level changes behind a configurable quiet window
(one second by default) and a fixed maximum window (ten seconds by default).
The occurrence includes paths, event types, counts, and timestamps; Ponderosa
does not automatically read or inject changed file contents. Missed schedules
produce one recovery occurrence. Exact interval histories may use an arithmetic
range when an explicit timestamp list would exceed the bounded payload;
high-frequency cron history is explicitly truncated and advances to the next
future fire rather than creating a Run storm.

Webhook senders authenticate the exact raw JSON body with HMAC-SHA256 over
`timestamp.eventId.body`. The event ID is inside both the signature and
idempotency boundary. Secrets are generated by Ponderosa, returned only on
creation or rotation, encrypted at rest with a host-local owner-only key, and
never returned by read APIs. Timestamp replay windows and a 256 KiB body limit
are enforced before occurrence creation. Signature validity proves sender
possession of the secret; it does not make payload text trusted instructions.

The operator-authored Trigger instructions and external occurrence payload are
separate structured fields. Provider input labels payload and provenance as
untrusted event data that can never grant authority or replace the trusted
instructions. V3.2 deliberately provides no reduced-authority execution mode:
automatic Trigger Runs have the Agent's full configured local access. The UI
must disclose that fact at creation and inspection. This is risk reduction, not
a security sandbox; users should connect only trusted senders and write narrow
instructions.

An optional Trigger Run budget is charged atomically when the scheduler leases
one root Run for that Trigger. Multiple compatible occurrences in the same
bounded batch cost one unit. Descendant work, coordination Requests, steering,
continuations, and Join resumptions are not charged. At exhaustion, occurrences
remain queued and the Trigger becomes ineligible for leasing until its period
resets or the operator adds a current-period allowance. Unlimited is the
default.

Decisions are first-order actionable input, not ordinary Collaboration. A user
response creates one human-priority Activation for the exact asking Agent.
Decision status and notification state remain durable even if the response is
handled in a later Run.

## Request state machine

Nonterminal states are `open`, `in_progress`, `waiting_dependency`, and
`awaiting_answer`. Terminal states are `completed`, `blocked`, `failed`,
`cancelled`, `superseded`, `recipient_unavailable`, `outcome_unknown`, and
`expired`.

Every request explicitly chooses a lifetime:

```ts
type RequestLifetime =
  | { kind: "deadline"; at: string }
  | { kind: "indefinite" };
```

The exhaustive reducer table is authoritative:

| Update | Allowed source | Result |
| --- | --- | --- |
| `progress` | any nonterminal except `awaiting_answer` | `in_progress` |
| `waiting_dependency` | any nonterminal except `awaiting_answer` | `waiting_dependency` |
| `dependency_resolved` | `waiting_dependency` | `in_progress` |
| `question` | any nonterminal without a question | `awaiting_answer` |
| `answer` | `awaiting_answer`, correlated to its open question ID | `in_progress` |
| any terminal update | every nonterminal | the matching terminal state |

Only one blocking question may be outstanding per request. `blocked` means the
request cannot continue without replacement or a new request;
`waiting_dependency` is temporary. Terminal requests reject mutation. Exact
idempotent replay of the same authenticated actor, scope, key, and payload is
safe and is handled before reduction.

Authorization is checked before reduction:

- recipient: `progress`, `waiting_dependency`, `dependency_resolved`, `question`,
  `completed`, `blocked`, `failed`;
- requester or user: `answer`, `cancelled`, `superseded`;
- system only: `recipient_unavailable`, `expired`;
- runtime supervisor/system or explicitly authorized user: `outcome_unknown`.

Request deadlines and join deadlines are independent. A request deadline moves
only that request to `expired`, reevaluates its joins, and activates a surviving
requester only when action is needed. Expiring a join never expires its requests.
Unknown coordinate fields are rejected before mutation; `deadlineAt` is the only
join-deadline field. A requester may cancel or supersede its exact open outbound
Request from a later authoritative Run without gaining mutation authority over
any other historical Request.

## Join state machine

A join stores immutable request IDs, a mode (`all`, `any`, or `quorum`), and a
wake policy. `each_result` creates a deduplicated progress Activation whenever a
new member becomes terminal while the Join remains open; results that arrive
before dispatch coalesce into the same Run. `final_only` suppresses intermediate
wakes. Both policies create exactly one terminal Activation when the Join ends.
It moves from `open` to exactly one of `satisfied`, `impossible`, `expired`, or
`cancelled`. Satisfied, impossible, and expired joins activate their surviving
owner. A join cancelled by its owner closes without creating a redundant
activation.

The server records the requester's canonical reply route on every outbound
Request. Only outcome and Join Activations back to that requester inherit the
route, so `ponderosa_message({text})` remains valid in progress and terminal
continuations without granting the recipient authority to reply to the
requester's user. Aggregate Join members must agree on one non-null route or
the resumed Run requires explicit routing.

When a request recipient creates a join while handling that request, the join
durably records the inbound request as its continuation. Creating the join
moves that request to `waiting_dependency`; completing the current Run does not
make its outcome unknown. An intermediate progress Activation reattaches the
continuation without making it terminally actionable: ending that Run returns
the continuation to durable waiting. A concurrently queued terminal Join
Activation also preserves the continuation. The terminal join Activation
reattaches the continuation request to the resumed Run so
`ponderosa_update_request` resolves
it authoritatively. The join Activation includes the continuation's durable
payload and an explicit terminal-update obligation. If the resumed Run ends
without fulfilling a still-suspended continuation, the supervisor transitions
it to `outcome_unknown`; it must never remain parked without a Run or actionable
Activation. An exact equivalent join—including its continuations—is reused even
after satisfaction or impossibility; immutable outcomes cannot justify a
duplicate wake.

Superseding terminates the original request. A replacement request uses a new
join; V3 has no mutable logical slots. Deleting a join owner cancels its open
joins and invalidates their pending activations transactionally. Deleting a
recipient transitions its open requests to `recipient_unavailable` and
reevaluates affected joins.

## Scheduling and failure invariants

The governing execution invariant is:

> Every actionable event becomes an Activation. Only the scheduler may attach
> an Activation to a Run or create a new Run.

Actionable events include directed human work, coordination requests, answers,
questions, blockers, terminal joins, triggers, deadlines, recovery decisions,
and steering. Informational broadcasts are passive: their communication event
is durable, but they create no Activation and wake no agent. Communication
creation and the decision to create its deduplicated Activation are one SQLite
transaction.

An ordinary agent message sent to the requester after that same provider
execution has terminally updated its attached correlated Request is also
passive. The complete message remains durable and auditable, while the Request
or Join remains the sole wake authority. This rule is recipient-specific:
unrelated recipients remain actionable, and explicit urgent messages always
override it.

An Activation is an actionable cause, not an instruction to create a new Run.
The scheduler alone decides whether to attach urgent steering to the current
authoritative Run, retain passive input without waking, queue work for a later
Run, or create a Run when no compatible execution exists. No HTTP handler,
delivery queue, runtime adapter, or compatibility path may create or claim a Run.

An agent is `running` with an authoritative active Run, `runnable` with an
actionable Activation, `waiting` with neither of those while it owns an open Join
or is recipient of an `awaiting_answer`/`waiting_dependency` request, and `idle`
otherwise.

Activating an agent for a human message, question, or urgent event never cancels
its joins. The Run handles the activation and the agent returns to waiting if its
join remains open. Explicit cancellation is an immediate control-plane action:
it fences the Run, interrupts the provider, and records the outcome without
waiting in a priority lane.

Priority is human/steering, agent question or urgent event, actionable join
problem, satisfied join, new request, ordinary message, then passive progress.
The scheduler coalesces compatible activations once, preserves every source ID,
enforces centralized concurrency and fairness, and assigns a monotonically
increasing fencing token to each lease.

A provider-confirmed entitlement denial blocks scheduler leasing for every Agent
configured on that engine without consuming delivery attempts or creating failed
Runs. Authentication files remain configuration evidence only. The denial is
durable across restarts and is cleared only by an explicit adapter-owned provider
check or a successful provider Run; elapsed time and ordinary readiness polling
cannot clear it.

An explicit operator-selected Queue is a semantic turn boundary. Queued human
communications are leased FIFO, exactly one per Run; compatible background
Activations may coalesce, but a later queued human turn is never consumed by an
earlier completion contract.

An activation is retryable on another Run only before prompt injection. Once the
prompt was injected, the scheduler resumes that same Run when possible; otherwise
it records `outcome_unknown`. It never blindly replays an injected prompt.

Human steering is the bounded exception for deterministic operator recovery, not
a reinterpretation of the uncertain delivery. A newly uncertain steer gets a
durable ten-second grace record. At its deadline, the scheduler fences and
interrupts only the originating Run and creates a new linked Activation whose
prompt first audits current state, preserves completed results, and then handles
the original user message exactly once. The operator may choose to let the
originating Run finish, which creates the same recovery Activation without
interrupting it. The original injection remains `outcome_unknown`; the recovery
is separate evidence. Historical uncertain injections have no grace record and
remain inert.

Every provider prompt or steering injection has a durable identity and lifecycle:
`pending -> submitted -> acknowledged`, with `outcome_unknown` as the fail-closed
terminal state. A provider session reference alone never proves whether a prompt
was submitted. Recovery may resume the same Run only when the provider can
reconcile the durable injection identity without resubmitting an acknowledged or
ambiguously submitted prompt.

Cancellation commits before provider interruption. One SQLite transaction
advances the fence, marks the Run cancelled, closes or releases its attached
Activations according to their policy, persists an idempotent cancellation
receipt, and enqueues a provider-interrupt outbox operation. Late provider output
is rejected by the advanced fence. Cancelling a child Run also terminalizes its
attached Request, reevaluates its Join, and creates at most one requester wake.
The interrupt is asynchronous and cannot roll back external effects that already
occurred.

After steering is acknowledged, uncorrelated output publication is fenced by the
newest steering injection ID. A pre-steer tool call cannot publish stale output
after newer instructions have been accepted, even if the provider emits it late.

Complete communications, request reports, and join outcomes remain durable in
SQLite. Prompt materialization is token-budgeted rather than semantically
truncated: it reserves room for human messages and blockers, may use summaries
and artifact references, splits large result sets into inspectable batches, and
exposes full-result retrieval. An overflow is explicit and actionable.

SQLite is the only runtime authority. Deleting JSONL telemetry cannot affect
scheduling, ownership, recovery, cancellation, or agent availability.

The cutover gate must prove:

- no code path creates a Run except the scheduler;
- every actionable cause has exactly one deduplicated Activation;
- passive broadcasts never activate agents;
- steering attaches without creating a competing Run;
- restart recovery cannot duplicate prompt injection;
- cancellation fences every late output;
- each terminal member causes at most one progress wake when enabled, and a
  terminal Join causes at most one final wake;
- provider failure at each transaction boundary recovers deterministically; and
- V2 scheduler files, tables, routes, and handlers have no readers or writers.

## Provider-visible tools

The coordination contract exposes three mutation tools and three read-only
discovery/retrieval tools to the model:

- `ponderosa_coordinate`: `{recipientAgentId,text}` is the common single
  delegation contract; `{delegations:[...]}` is common fan-out. The server
  derives stable idempotency, gives each Request an indefinite lifetime, and
  creates one aggregate all-results Join with `wakePolicy: each_result` by
  default. `completionMode: callback` preserves the legacy unjoined per-result
  wake, while `completionMode: record` stores and displays results without
  waking the requester. Ordinary final-only fan-out stays on the common form
  with `completionMode: join` and `wakePolicy: final_only`. The advanced request
  array and Join fields are reserved for quorum/any conditions, custom
  per-request lifetimes, existing-request recovery, and custom satisfying
  outcomes.
- `ponderosa_update_request`: `{text}` is the common canonical report and
  `{question}` is the common correlated blocking follow-up. The former completes
  the sole Request attached to the Run; the latter asks its original requester.
  Both derive a stable update ID.
  Advanced kinds and exact IDs remain available for progress, questions,
  failure, multiple attached Requests, and authorized historical mutation.
  When exactly one correlated request is attached to the current Run, the model
  omits `requestId` and the server resolves it from SQLite's durable Run-to-
  Activation linkage. Multiple attached requests require an exact ID; the server
  never uses fuzzy identifier matching.
- `ponderosa_message`: `{text}` replies to one uncorrelated canonical incoming
  Communication. The server inherits its audience and visibility and derives
  stable idempotency. Ambiguous/non-message Runs require explicit intent and
  recipients. One inferred material reply is allowed; exact transport retries
  replay it.
- `ponderosa_team_directory`: retrieves the current run-scoped Team Chat roster
  or one focused Agent entry without relying on provider shell/network access.
- `ponderosa_context`: retrieves paginated older scoped history only when the
  current Run advertises that bounded context omitted it.
- `ponderosa_result`: retrieves ordered, byte-bounded pages for stable
  `ponderosa://activation/<id>` and `ponderosa://artifact/<id>` references that
  are reachable from the current authoritative Run. Its signed cursor is bound
  to that Run, reference order, content versions, and byte budget. Retrieval is
  read-only and never creates scheduler or communication state.

“Coordinate and wait” is a skill/helper around `ponderosa_coordinate`, not a
fourth runtime tool. All tool mutations commit SQLite state and an outbox record
atomically; scheduling side effects occur only after commit.

Provider context is shaped, not flattened. Every prompt section has a declared
role: authoritative identity/policy, action-required current work, relevant
bounded history, or an on-demand reference. A versioned policy snapshot is sent
once per provider-session epoch, the full Team Directory is fetched through a
Run capability only when needed, and fresh-session private history is restricted
to the active Project chat. Older scoped history remains durable behind a
paginated Run capability. Every Run persists the exact text Ponderosa submitted,
its hash, and a manifest that distinguishes submitted material from state known
only to remain in a continued opaque provider session.

Ponderosa does not silently rewrite or redact prompt material. Secret detection
and redaction require an explicit, inspectable product policy so reconstructed
provider input cannot differ invisibly from what was actually supplied.
