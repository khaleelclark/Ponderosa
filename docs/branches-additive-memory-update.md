# Add memory when updating an installed workflow

A full workflow package can add selected new Agents and their memory to existing Chats. In the import dialog, choose **Select additive memory update**, select new Agents' private memory and any preserved Chat's team memory, then review both the incoming records and existing destination inventory before confirming. No records are selected by default. Existing Agents' private memory and history are preserved; incoming data for those Agents is excluded. The preview names excluded source row counts. Team data is carried once by a selected new Agent in that Chat, including when the exported team snapshot was attached to a preserved source Agent.

This additive mode requires the same installation package identity, preserves every installed Chat and Agent, and adds Agents only inside existing Chats. Review removals, new Chats, or another package identity separately. Existing Agent management permissions, destination capability policies and memory grants remain authoritative. New Agent settings are shown in the usual full-context review. Source grants, credentials, global memory and live execution authority are never transported through this path. The separately reviewed global-memory transfer remains unchanged.

The public preview body adds `memorySelection: {newAgents:[{chatRef,agentRef}],teamChats:[chatRef]}`. The response adds `memoryUpdateReview`, with exact selected incoming snapshots, existing destination snapshots, selection and excluded-row count. An immutable server-side installation plan binds this reviewed package and selection to the current destination memory inventory and normal resource/version/configuration revisions. Confirmation requires both `acknowledgeFullImport:true` and `acknowledgeMemoryUpdate:true`. Missing selection on memory-bearing updates, selection of an existing Agent, unknown/duplicate selections, source record collisions, changed destination memory/settings, or unsupported source bindings refuse with a visible error. A new preview is required after destination changes; an old plan never silently adopts them.

Selected snapshots pass the existing memory signature/vector/scope/lineage/conflict/secret validators. The ordinary package importer remaps local provenance and deterministic package-owned IDs, preflights collisions, and never replaces destination facts. Private data is scoped to the newly created Agent; selected team facts and conflicts append in parallel without reconciliation or deprecation of existing facts. Exact completed staged receipts are checked again on retries before publication, so edited IDs are refused instead of overwritten. Exact retries add only missing package-owned records.

All imported rows stay hidden while their Agent's workflow installation is staging, even for existing Chat peers. The installation promotes its resources and publishes its workflow together in SQLite. If publication fails, prior Chat/Agent settings are compensated using the existing journal; new Agent/memory rows remain hidden for retry. Completed staged import receipts retain their exact memory cleanup plan. Canceling or requiring a new review first retires staging, then removes only rows with the matching package-operation ownership and the staged Agent. Foreign records refuse cleanup and retain a visible error. Ordinary active/published imports cannot use this staged cleanup authorization.

This coordinates SQLite receipts with nontransactional external Chroma writes; it does not promise a cross-store transaction or cross-process writer isolation. Existing write-failure compensation and retained cleanup receipts provide retry/recovery, not arbitrary external-effect rollback. Full-machine copying, multi-Chat remapping, in-place replacement of existing Agent memory and general historical execution recreation remain separate portability work.

## Controlled mounted check

The manual fixture `tests/branches/additive-memory-mounted.tsx` mounts the production package dialog and React Query. `tests/branches/additive-memory-mounted.browser.mjs` drives desktop and emulated-phone cells through real Fastify installation routes and owned synthetic Chroma data, using the same setup as the additive storage regressions. With existing dependencies, Chrome, Playwright ffmpeg and offline memory fixtures, set fresh `PONDEROSA_ADDITIVE_MOUNT_BUILD` and `PONDEROSA_ADDITIVE_MOUNT_EVIDENCE` directories. Build with `node apps/web/node_modules/@rsbuild/core/bin/rsbuild.js build --config tests/branches/additive-memory-mounted.config.mjs`, then run `node --import ./tests/shared/workspace-resolution.mjs --test --test-concurrency=1 tests/branches/additive-memory-mounted.browser.mjs`. No dependency installation or real provider is part of the check.

The check exercises explicit private/team selection, complete incoming/destination memory snapshots in the Before/After accordion, both acknowledgements, Tab/Enter/Space navigation, pending Escape cancellation and late-response exclusion, review/status errors and retries, Back and selection reset, stale destination refusal, staged cancellation compensation and a new reviewed successful update. Review starts with focus on the available Cancel action so disabling its trigger does not strand keyboard focus. Status snapshots are observed without writing them back into their own query cache, allowing the normal polling interval and status retry to progress. Existing private data, global rows, management permissions, capability policies and grants are compared after the controlled operations. This is component-level qualification; it does not certify all navigation shells, screen readers/themes, general migration, cross-process recovery or full Phase2.
