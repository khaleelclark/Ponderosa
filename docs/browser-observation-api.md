# Owned browser console queries and explicit recordings

These APIs use the existing `POST /api/agent-browser` transport and its server-issued active Run capability. They operate on the browser already selected by that Run. They never launch a browser, discover an operator account, infer a saved-browser grant, or select another Chat's session. Both a live exact owner/Run and Agent control are required, including for a console query. A paused native connection must be explicitly resumed first. Local transports without these driver operations fail as unavailable.

Managed tools:

- `ponderosa_browser_console({query?: {after?, limit?, pageId?, level?}})` returns `{entries, next, truncated}`. `level` is log, info, warning or error. Each entry has a sequence, receipt time, opaque page ID and redacted text. The 500-entry session ring keeps at most 4,000 characters per entry. Query returns 50 entries by default, at most 100; it does not clear history. Pass `next` as the next `after` cursor with the same filters. Reset the cursor when the browser/driver session changes. `truncated` reports eviction since the cursor. Console calls and uncaught JavaScript exceptions come from actual CDP Runtime events, not from page DOM scraping. The existing live console audit callback remains in place.
- `ponderosa_browser_recording_start({page_id})` explicitly starts collection for one inspected opaque page ID and returns `{id, pageId, startedAt}`. One recording is retained per driver, bounded by 60 seconds, 120 frames, or 8 MiB of encoded frame strings. It consumes real CDP `Page.screencastFrame` events from the existing acknowledged preview stream. It does not record audio, an entire desktop, other tabs, or an encoded video.
- `ponderosa_browser_recording_stop({recording_id})` freezes collection and publishes a managed JSON artifact with format `ponderosa.browser-recording.v1`, timestamped base64 JPEG frames, start/end receipt times, page ID and explicit stop/limit/page-close reason. It returns the ordinary managed artifact ID/reference/path, frame count, media type and reason. Decode each `jpeg` to image bytes and present at its `atMs` offset to replay. Page paints are event-driven, so a static page may produce few frames. An empty recording fails visibly without publishing an empty artifact and allows a fresh start. It is not described as a video file.

The equivalent transport operations are `console` with `query`, `recording_start` with `page_id`, and `recording_stop` with `recording_id`. `BrowserObservationClient` and the DTOs are exported by `@ponderosa/core`; supply its generic `call(operation, input)` transport from the existing authenticated Run client. It does not acquire credentials or grants.

The original Run and control epoch own a recording. Operator takeover, native disconnect, browser close or broker-client suspension discards unpublished buffers; a successor cannot stop an earlier Run's recording. After a successful publication, a repeated stop of the same ID returns the same receipt until another recording starts. Byte publication and the generated-artifact event use the existing managed storage and exact Run event authority; a changed grant cannot publish a catalog entry. Limits finish collection but still require explicit stop to publish. Pixels may contain visible sensitive user data, just as an explicit screenshot may; callers should request a recording deliberately.

Implementation-only delivery: execution is deferred by the operator's implementation-first direction. Existing browser-control fixtures now include bounded query, recording freeze/limits and real broker/manual-control cases. The opt-in native-browser fixture writes assertions for actual Runtime console messages and JPEG screencast frames. None was executed for this change. There is no web UI change, encoded-video export, audio capture, automatic recording, or full native-parity qualification claim.

Protocol references: [CDP Runtime consoleAPICalled](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#event-consoleAPICalled), [Runtime exceptionThrown](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#event-exceptionThrown), [Page screencastFrame](https://chromedevtools.github.io/devtools-protocol/tot/Page/#event-screencastFrame), [Page screencastFrameAck](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-screencastFrameAck).

## Operator REST contract (source successor)

Operator observations use ordinary operator REST access and the application's existing origin protection. Ponderosa is a single-operator self-hosted service without a new login/token layer here (Bible #7/#20). These routes do not accept an Agent capability, borrow an Agent grant, open a browser or change control. Take operator control through the existing explicit control route first; native manual/private-sign-in mode must be explicitly resumed before observations are available. Obtain the current session ID, control epoch and admitted opaque page IDs from the existing browser session response; never reuse identities across sessions.

Two existing route bases are supported:

- Shared owned Chat/saved browser: `/api/projects/:ownerHandle/browser`. Pass the explicit canonical Chat owner handle (`chat:v1:<conversationId>`) or `saved-browser` exactly as existing browser controls do. The existing pre-handler resolves and validates live Chat/namespace ownership; namespace-only ambiguous ownership is rejected. Console query only is currently supported here.
- Private Agent browser: `/api/projects/:projectId/agents/:id/runs/:runId/browser`. All observations require the exact currently active Run and canonical Agent/Chat/Project membership, including when the operator controls input. No access survives Run termination, deletion, session replacement or an expired control epoch. Recording publication is supported here because an exact existing Agent/Run/Chat owns its artifact provenance.

All four operations are POST, return `Cache-Control: private, no-store`, and use JSON. Each requires `sessionId: string` and `expectedControlEpoch: number` from the current inspected session. Bodies and responses:

| Suffix appended to route base | Additional body fields | Response |
| --- | --- | --- |
| `/observations/console` | `query: {pageId, after?, limit?, level?}` | `BrowserConsoleResult`: `{entries, next, truncated}` |
| `/observations/recording/start` | `pageId: string` | `BrowserRecordingStatus`: `{id, pageId, startedAt}` |
| `/observations/recording/stop` | `recordingId: string` | `BrowserOperatorRecordingResult`: `{artifactId, artifactRef, path, mediaType, frames, reason, downloadUrl}` |
| `/observations/recording/status` | none | `BrowserOperatorRecordingResponse`: `{recording?: {id, pageId, startedAt}, artifact?: BrowserOperatorRecordingResult}` |

Operator console queries require an admitted page ID, including a second admission check inside the serialized driver action. Filters, cursor limits, redaction and eviction semantics are the same as the Agent console API. Start requires the current active page from the inspected session and rechecks the actual driver's active page inside the queue, rejecting a tab change. Start/stop/status require operator control and the same session/epoch throughout the queued action. The recording also retains its original owner (`operator` versus `agent`); Agent tools cannot consume an operator recording. A new control owner, native disconnect/manual transition or session lifecycle change fences old requests and buffers. Browser-service suspension discards unpublished frames; status after a lost connection is not a durable recording archive.

The stop response's `downloadUrl` is the existing `/api/projects/<actual namespace>/artifacts/<artifactId>/download` route, never an owner-handle namespace or host path. Publication preserves the real originating Agent/Run and its Chat membership; the generated-file registry verifies managed bytes against the exact catalog identity before stop succeeds. The existing artifact download route independently checks operator Project access and immutable generated-file authority. Standard operator Project audit access can read the published artifact after Run end; this endpoint does not make it available to a different Chat's Agents or borrow a saved-profile grant. Recording data remains only `ponderosa.browser-recording.v1` timestamped JPEG-frame JSON, with the existing limits and no MP4/audio.

**Explicit narrower boundary:** shared Chat and saved browser recording start/stop/status return HTTP 409 with `code: "operator_recording_unavailable"`. They have no canonical operator-owned Chat artifact publisher, and this change does not fabricate an origin Agent, select a Run or infer a grant. The shared-browser UI may expose console queries, but must display recording as unavailable rather than route it through `/api/agent-browser`. Full shared-browser operator recording remains implementation work requiring canonical Chat-owned artifact provenance. Local drivers lacking console/recording methods return a visible HTTP 409 unavailable error without launching a replacement or falling back to another session.

Recovery and unknown outcomes:

1. Do not automatically retry start or stop POSTs after timeout/disconnection. The operation may already have happened. No request-id idempotency contract is added.
2. With the same live session/epoch, call the read-only `recording/status` POST. It joins the same action queue: a successful start is returned as `recording`, and a successful stop returns the original managed receipt as `artifact` (including `downloadUrl`). Status is safe to repeat; console queries also do not mutate or clear their retained ring.
3. A deliberate repeat stop of the same recording ID under the same authority returns the same retained receipt without publishing again. Starting another recording replaces that recoverable receipt. Serialize the controls in the UI; do not issue multiple starts concurrently.
4. A missing receipt, status error, changed session/epoch, ended Run or publication error does **not** prove the operation never happened. Preserve the unknown-outcome message and inspect ordinary Project artifacts before a deliberate new attempt. Publication may have persisted before a transport/registry failure. Status is in-memory, not crash-durable operation history.

Shared DTOs plus `BrowserOperatorObservationClient` are exported by `@ponderosa/core`. Supply a POST adapter rooted at one of the existing owned-browser bases; its suffixes omit the leading slash. The SDK performs no retry, capability discovery, ownership selection or control takeover. Web UI is intentionally owned by its separate writer.

Deferred fixtures in `tests/browser/browser-control.test.mjs` cover exact operator session/epoch/Run/page admission, active-tab races, lost-response receipt recovery, repeated stop publication count, owner handoff fencing, shared browser console/no fabricated recording provenance and unavailable drivers. They have **not been executed**. No build/typecheck/browser/native/Node execution or whole-Bible validation was performed for this successor.
