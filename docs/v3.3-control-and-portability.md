# V3.3 Control and Portability Contract

V3.3 completes the product controls needed before the next interface redesign.
These are domain contracts, not temporary UI conventions.

## Rules, providers, and identity

- Workspace rules apply to every Agent. Project rules apply after Workspace
  rules and before Agent/history context. Ponderosa stores both directly; it
  does not try to keep `AGENTS.md` and `CLAUDE.md` synchronized.
- A rule change lets an active Run finish, then forces a fresh/reseeded turn so
  the next provider input uses the new effective rules.
- Provider enablement is a global operator preference. Disabling a provider
  lets active Runs finish and holds queued work without consuming attempts.
  Re-enabling it resumes leasing, subject to durable provider availability.
- One operator profile supplies the display name, `#handle`, and a catalog
  avatar. It changes presentation and mentions, not authorization.

## Operational visibility and notifications

Team chat combines authored Collaboration messages with a derived operational
timeline. Runs, queued work, Requests, waiting conditions, Trigger work,
Decisions, and organization changes appear as short human-readable events such
as “Reviewer is running” or “Manager is waiting for one more result.” These are
projections of canonical state, never synthetic chat messages or a second
authority.

Notifications have an explicit severity (`info`, `attention`, or `urgent`),
status (`open`, `resolved`, or `dismissed`), stable deduplication key, and an
optional action. Provider failures, exhausted Trigger budgets, and unresolved
Decisions remain visible until the condition is resolved or dismissed.

The **Agent work** inspector is the drill-down for that compact timeline. It
groups structurally connected Requests, Joins, Activations, scheduler/provider
Runs, Trigger occurrences, and Decisions into one chronological trace. Links
come only from authoritative coordination tables; the inspector never infers a
relationship from message text and never writes state. Team-chat operations,
Agent Run cards, Trigger history, and relevant notifications may open a focused
record. Plain-language state is shown first, while IDs, fences, dispatch policy,
prompt hashes, bounded payload previews, and failure details remain available
under technical details. Agent-scoped views retain the bounded connected
requester/wait chain rather than hiding records owned by another Agent, and
explicitly disclose when older work exceeds the safety limit.

## Decisions

A Decision is a durable Agent question addressed to the operator. Its mode is
approval, Agent-defined choice, or free text. Approval and choice always permit
“Something else.” A blocking Decision means the Agent has no safe independent
work left; it does not claim that the host sandbox makes the action impossible.

The response is preserved with the original question and wakes the exact Agent
through normal Activation scheduling. Deleting an Agent or changing its
reporting line through Agent management requires a resolved approval Decision.
Stopping, creating, and renaming descendants may be autonomous.

## Agent organization management

An active Agent can discover only its visible descendant subtree. Organization
mutation uses three stages: `describe`, exact idempotent `plan`, and Run-scoped
`apply`. A plan cannot target another Project, an unrelated branch, a
provider-native helper, or the Agent itself. Every applied change uses canonical
Agent lifecycle APIs and appears in operational Team chat.

## Trigger Run budgets

A Trigger budget limits outside activations, not all downstream work. The unit
is one root Trigger Run. A same-Trigger batch costs one unit; child Runs,
continuations, steering, Requests, and Join resumptions cost zero units. Budgets
are optional and unlimited by default. Periods are day, week, month, and
lifetime.

At the limit, every new occurrence remains durable and queued. The operator may
add a bounded number of Runs to the current period; a period reset clears usage
and temporary allowance. Ponderosa does not estimate money for this control.

## Import and export

Portable JSON packages have two user-facing modes. Copy and Download expose the
same choices for an Agent, its descendant organization, and the readable chat
transcript:

- **Template:** initial Agent instructions and organization layout only.
- **Full:** effective private history, all managed generated artifacts, disabled Trigger
  definitions, engine/model preferences, and organization layout.

Import accepts either a selected JSON file or pasted JSON and requires an
explicit engine mapping. Imported Triggers are disabled and receive new secrets.
Destination Workspace and Project rules are authoritative; source Project rules
remain package provenance and are not submitted to the provider. Imported
messages retain effective provider history but do not appear as newly authored
messages in the destination chat.

Managed generated artifacts are Project-owned and survive deletion of their
originating Agent. Import preserves an artifact ID when it does not collide and
otherwise assigns a new stable ID and rewrites private-history references. The
JSON transport currently limits embedded artifact bytes to 64 MiB per package.

## Agent-accessible API boundary

Ponderosa capabilities are discoverable to active Agents and carry full Agent
access, but they are never ambient host credentials. Runtime tokens are scoped
to the exact authoritative Run. Coordination, Decisions, organization
management, browser access, and messaging validate that capability before any
mutation. Idempotency and canonical audit records are required for retryable
operations.
