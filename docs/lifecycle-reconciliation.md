# Operator lifecycle reconciliation

All endpoints inherit the existing origin and operator request boundary. Agent capability tokens are refused. These operations neither replay unknown effects nor turn retained historical Communication into a fresh result. No execution qualification has run.

## Retained package evidence

`GET /api/lifecycle/checkpoint-custody` lists retained custody identities (bounded to 1000).
`GET /api/lifecycle/checkpoint-custody/:id` returns `CheckpointCustodyLifecycleEntry`: current state, source membership where available, canonical reference surfaces, drain blockers, exact file names/lengths/SHA256 and a review digest. File bodies never enter the response.

`POST /api/lifecycle/checkpoint-custody/:id/reconcile` accepts `{commandKey,reviewSha256,preserveEvidence:true}`. Admission runs in the canonical IMMEDIATE transaction and existing package admission queue. Every current Branch/coordination JSON receipt/reference is conservatively searched; references are never removed to make a review pass. Source executions must be terminal or absent, provider/scheduler authority and unresolved creation custody drained, and the process-wide writer/capture registry idle. Changed proof, bytes, source state or key refuses. The operation records a durable manifest and tombstone, then moves owned regular files to private `checkpoint-package-custody/reconciled/:id`. Every original byte is preserved. Interrupted moves resume with the same exact command, checking the retained manifest and refusing unexpected bytes. A reconciled capture identity cannot be captured, read or admitted again.

This reclaims the active namespace, not disk bytes. It does not unlink user originals or last surviving private package evidence. Symlinks, hardlinks, special files, oversized inventories and unrecognized changed bytes refuse. Referenced historical packages, admitted destinations and unresolved import pins remain retained until their canonical owner performs its own retirement protocol. No row is deleted to bypass a RESTRICT constraint.

## Failed remote memory effects

Future remote writes record exact collection scope, memory/conflict collection and operation in their existing durable unsettled hold. This describes the failed call; it is never replayed. Reads remain read-only.

`GET /api/local-memory/mutation-holds` lists current hold identities/digests and effect metadata.
`GET /api/local-memory/mutation-holds/:id` returns `MemoryMutationReviewDto`: hold digest, bounded backend readback digest/count, required operator drain evidence and a review digest. Two consecutive readbacks must agree while all registered host writers are drained. The existing memory authority exclusively serializes these reads. Backend rows and vectors stay private.

`POST /api/local-memory/mutation-holds/:id/reconcile` accepts `{commandKey,reviewSha256,backendDrainEvidence,preserveCurrentBackend:true}`. The local operator must FIRST stop or independently reconcile remote work and describe the observed backend drain. A text field is operator testimony, not a fabricated server result-query proof. Stable reads alone cannot prove that an unobserved remote worker will never write later. The endpoint re-observes current backend state, requires the exact review and no intervening host writer/capture, then durably retains the complete observed collection bytes, original hold and immutable local-operator decision before retiring that one hold and registry uncertainty reason. It never modifies backend memory, provenance, grants or unrelated holds. Same-command readback resumes interrupted hold retirement; changed input or missing/corrupt retained evidence refuses.

Legacy holds have no exact effect metadata and return `canReconcile:false`; they remain held. No timestamp, process restart, guessed scope or broad clear operation releases them. External backend result-query/reconciliation is still required for cases the operator cannot settle. The operation accepts the preserved current backend state as the new human-reviewed baseline, not a claim about whether the original write succeeded.

## Background package import ownership

`GET /api/lifecycle/agent-imports/:id` reads retained operation evidence even when its original Chat owner is deleted. It returns `AgentImportLifecycleReview`, including the exact canonical creation receipt identity, blockers, mutation-free disposition and review digest. `POST /api/lifecycle/agent-imports/:id/reconcile` accepts `{commandKey,reviewSha256,action,note}`. `preserve_unresolved` durably holds the existing operation without rewriting an unknown effect as a failure or replaying it. `retire_mutation_free` is admitted only with no committed import, no Agent/artifact/result effects, a still-preparing or absent canonical creation operation, and no canonical owner/admission reference. It marks only that proved-empty operation rolled back, durably holds its submission identity and completes the background journal as failed. Actual created/reserved identities and admission pins cannot take this path.

Every background retry checks the durable lifecycle hold before reading/importing payloads; synchronous reuse of the same admitted submission also refuses. Exact-command readback finishes an interrupted mutation-free journal transition. The original payload remains preserved. Startup now moves abandoned regular upload/copy/temp payloads to private `agent-import-operations/retained-orphans` instead of unlinking them; their bytes continue to count against staging admission capacity. `GET /api/lifecycle/agent-imports/orphan-evidence` lists bounded retained names/sizes without exposing source bodies. These bytes cannot be silently deleted to make room. Lifecycle hold receipts and canonical import/owner receipts remain separate evidence.

## Existing Agent regrouping disposition

Same-Chat reporting changes already use `PUT /api/agents/:id/manager` in `routes/agent-maintenance.ts`, delegating to canonical `AgentStore.updateAgentOrganization` / `store-agent-management-authority.ts`. It preserves Agent identity, history, private resources and working roots, validates active same-Project/same-Chat ancestry and refuses cycles. Branch installation likewise calls this canonical writer for explicitly bound existing Agents. No duplicate reparenting backend is needed for that independent capability.

Cross-Chat existing-Agent relocation and rebinding existing Shared working roots remain unsupported. Those operations require coordinated source/destination Chat policy, private-memory ownership/audiences, role bindings, pending Requests/Joins, provider drain and working-copy ownership transactions; changing `conversation_id` or a root path would violate current invariants. New package import continues to create fresh identities and locally owned roots. This disposition does not claim full portability/regrouping parity.

## Branch owner lifecycle integration

`POST /api/lifecycle/branch-custody/review` accepts `{source}` and returns the canonical Branch custody inventory: exact references, current owner state, cleanup/drain blockers, abandonment blockers, revision and release eligibility. Source is the original `CheckpointPackageSource`, not a caller-declared list of references. `POST /api/lifecycle/branch-custody/retire-checkpoints` accepts `{source,commandKey,expectedRevision,checkpoints:[{id,sha256}]}`. It retires only the exact explicitly selected history after current CAS, settled ownership/drain, complete lineage and admission checks. No automatic history selection or initial-checkpoint retirement is provided. Changed/referenced/unknown evidence refuses; original issued capture intent stays retained with a validated disposition. Full original selected snapshot rows, including serialized bytes, are archived in the same atomic retirement receipt before executable rows retire. Exact command replay returns the canonical Branch receipt.

Package custody review now composes `BranchCustodyLifecycle.inspect` from the live BranchStore, plus retained graph-restoration references and independent runtime/creation/writer blockers. Validated Branch audit dispositions do not remain executable package pins. Unknown scheduler outcomes and pending/attached/retry/unknown activations still block. Reconciliation runs inside the root transaction immediately before durable filesystem tombstone publication; package namespace retirement prevents later capture/read/admission. All source and package bytes remain preserved. Deleted-owner custody requires actual deletion/cleanup receipts; owner absence alone never proves drain.

## Integrated host protocols

The previously missing destination-specific host adapter/operator retirement routes and combined package/Branch capture abandonment journal are implemented below. Retained provenance, referenced resources, missing native/effect proof and legacy unknown holds remain explicit refusals. These are source implementations, not executed qualification.

## Destination retirement operator protocol

The host adapter and routes now implement the destination boundary described above:

1. `GET /api/lifecycle/destinations/:id/review` returns the Runtime review/hash plus `canReleaseSourcePins`, `preserveOnlyPermanent:true` and `globalRuntimeQuiescenceRequired:true` for the operator choice. It requires actual completed destination Chat deletion/cleanup, completed Agent deletion receipts for the exact staged member map and all additional destination deletion tombstones, no surviving runtime/import/creation/request/join/native effect authority, and current local-operator Project ownership (or fully completed Project deletion receipts). Source owner absence never supplies destination exit proof. Canonically soft-deleted Agent audit rows may remain; live mapped identities still refuse, and complete matching deletion receipts remain mandatory. Agent deletion server cleanup is written only after the existing runtime drain and recovered provider-process exit paths succeed; current authority is independently rechecked.
2. `POST /api/lifecycle/destinations/:id/approve` accepts `{commandKey,expectedReviewHash,releaseSourcePins,authorizeDeletedOwner:true}`. The operator must explicitly approve this exact review and pin disposition. A private fsynced immutable decision binds all those fields. It is not provider-exit testimony and cannot replace deletion/drain receipts.
3. `POST /api/lifecycle/destinations/:id/retire` accepts the same exact choice. Runtime re-observes evidence and approval inside the canonical owner IMMEDIATE transaction. Changed authority, unknown effects, source references with `releaseSourcePins:true`, surviving identities or missing rollback receipts refuse. Successful canonical retirement archives admission/member evidence and establishes permanent dispatch/idempotency tombstones. `GET /api/lifecycle/destinations/:id/receipt` returns the durable result, including after source owner deletion.

Reference proof binds Branch's full source inventory/revision, all current package-custody metadata, import-operation metadata, matching cross-owner Branch commands and graph restorations. It excludes only this admission's own Branch `admission` reference. Every other source/owner/checkpoint/restore/package reference remains a pin. Bounded/quarantined/malformed inventories refuse. Package payloads remain retained; this operation never deletes them. Active/unknown background imports require a canonical rollback receipt and failed result-free operation, not a timeout or owner disappearance. Unrecorded failed imports remain held. Destination native attempts require recorded exit when process identity exists. Request/join effects must be terminal.

The live-host adapter deliberately requires global provider/runtime quiescence, including opening, reusable, closing, one-shot and retry authority. Unrelated active provider work can therefore block retirement. Remote-memory durable holds and process registry uncertainty also block; neither is cleared by retirement. Pre-stage reservations without a completed destination Chat deletion receipt remain held. `releaseSourcePins:false` is permanent preserve-only retirement; there is no later upgrade command. `releaseSourcePins:true` is usable only when *all* other source references have been canonically retired; retained issued checkpoints and owner commands still refuse. This operation does not introduce a cascading history/admission retirement command. Admitted historical provenance remains unsupported.

## Combined capture abandonment protocol

`POST /api/lifecycle/checkpoint-captures/abandonment-review` accepts `{source,captureKey}` and returns the combined Branch/package review hash, exact capture digest, Branch revision, package inventory digest, remaining references and blockers. `POST /api/lifecycle/checkpoint-captures/abandon` accepts `{source,captureKey,commandKey,reviewSha256,preserveEvidence:true}`. It serializes with package import admission and executes inside the canonical owner IMMEDIATE transaction.

A private fsynced prepare journal binds the exact human-reviewed source, original capture key/digest, full original canonical capture row (including its serialized bytes), Branch revision and package inventory. The original capture archive survives later Branch owner deletion and is hash-bound in the independent commit result. Branch's `abandonCapture` first validates the exact unsealed intent, canceled/terminal fenced owner, observed native/provider drain, resolved imports/requests/activations/resource effects, and absence of every reference except that exact capture's own cleanup pin. Only its synchronous validated callback may retire package custody under the filtered review. The callback fsyncs the inventory manifest and permanent package tombstone before moving every original into private retained evidence, then writes an actual digest-bound package-retirement proof. No constant receipt, guessed status, broad pin deletion or source deletion is used. A capture that never reached package staging can receive a zero-byte tombstone only through this validated Branch callback.

The Branch disposition and independent `host_lifecycle_commits` result are committed in the same SQLite transaction. Additive migration `0040_lifecycle_reconciliation.sql` retains the exact command/result/hash with no Branch/Chat foreign keys and immutable update/delete triggers. The original capture remains audit evidence; disposed identities cannot resume or seal. The package tombstone independently blocks capture/read/admission. The independent result enables exact-command replay after Branch owner deletion.

SQLite and filesystem durability are joined by a recovery journal, not a fictional cross-filesystem atomic commit. If filesystem publication succeeds but the SQL commit fails, the package remains safely tombstoned and the original Branch capture remains held; the exact unchanged command can resume and commit. Changed Branch evidence refuses and preserves the prepared evidence. If SQL commits before response loss, replay verifies canonical result, package receipt, manifest inventory digest and every retained original's length/hash without re-running the Branch disposition. Missing/corrupt/conflicting proof refuses. New unmatched late files remain preserved and held rather than discarded. The journal survives source Chat/Agent deletion. No source/user bytes or remote-memory holds are removed.

Deferred host fixtures in `tests/organizations/lifecycle-protocols.test.mjs` cover SQL-failure-after-package-publication recovery, owner-deleted exact replay, retained-byte corruption refusal, destination cleanup refusal independent of source absence, durable approval requirement and changed live-provider refusal. These are focused injected-host fixtures; real Branch/native/remote-backend crash qualification remains deferred. No tests/checks/types/build/Node/native/browser/runner preparation or execution occurred.

Retained package receipts now include `filesSha256` sealing the original file manifest. Exact replay checks bounded owned manifest evidence and every retained file digest/length. Older reconciliation receipts without that inventory seal remain held rather than receiving fabricated custody proof. This source-only successor performs no migration of historical filesystem receipts.
